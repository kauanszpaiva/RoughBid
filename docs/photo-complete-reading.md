# Complete photo batches

A photo purchase covers one immutable batch of 1–8 verified private images. It is a separate `photo_batch` item, not a synthetic PDF. The graph contains one observation pass per image, one reconciliation pass per unordered pair (one self-review for a single image), and one risk pass per image. There are 3–44 operations; every selected view and pair is included. These are separate model passes, not a claim of independent human certification.

The source images retain their original bytes and hashes. A supplied image that cannot fit the reviewed input/detail limits is rejected before checkout. The implementation does not silently crop, compress, sample, or discard it. A source failure, expired profile, malformed response, or unknown provider outcome preserves the checkpoint and requires review; it does not manufacture a completed result.

The fixed purchase price uses the sum of the reviewed worst-case operation costs, the explicitly configured batch overhead plus an overhead per selected image, one payment fixed fee, and the existing membership revenue margin. Both overhead settings are required, may explicitly be zero, and are frozen in the contract; there are no production defaults. Monetary sums use integer USD micros and round the total provider bound up to cents once. It is neither an observed AI bill nor a prediction of normal token use. Actual cost can be lower. Provider funding is separate from customer payment; account/model metadata does not prove available credits or successful inference.

Each operation freezes `reservationUsd = max(company base reservation, verified maximum call cost)`. The company cap remains a separate shared admission boundary. Provider/run authorization is the sum of those immutable operation reservations, with an exact operation count. Scheduling packs the ordered, indivisible operations into conservative company windows using current available headroom and subtracting unresolved exposure from every future window. A purchase is refused if an operation cannot fit that capacity or the schedule crosses the tariff expiry. Waiting can last multiple windows; it does not authorize extra charges or promise a completion date. Unknown outcomes retain exposure without an expiry and never authorize a replay. An existing waiting run has no ETA until settlement proves future capacity; its scanner and claim gates cannot wake it merely because time passed. A known cost's rolling window starts at settlement, never before the reservation.

`PHOTO_COMPLETE_PROFILE_JSON` must contain all three explicit routes, maximum reasoning, an unreduced output limit, current primary-source tariff snapshots, accepted input and output limits, any documented combined context limit, and all additional request charges. The snapshot explicitly attests standard uncached pricing, included reasoning tokens, and the maximum accepted input. No tariff is inferred from a model name. For Astra the complete path additionally freezes `service_tier: default`, `prompt_cache_options: {mode: explicit}` without cache breakpoints, no tools, and original image detail. The legacy photo adapter keeps its existing request policy.

Reviewed image input documentation (2026-10-03): [OpenAI images and vision](https://developers.openai.com/api/docs/guides/images-vision) documents a 512 MB request limit and Astra original-detail rejection above 30,000 32px patches; [Claude vision](https://platform.claude.com/docs/en/build-with-claude/vision) documents the 32 MB request, 10 MB base64 image, and 8000px limits; [Gemini image input](https://ai.google.dev/gemini-api/docs/image-understanding) documents the 20 MB inline request limit. These are static request constraints, not account inference attestations.

Checkout persists the actor's consent to the exact contract hash. Only a signature-verified live payment with matching account scope, session, amount, currency, actor and contract starts its unique run. A lost queue acknowledgement retries that same run. A URL return or GET only reads saved state. Refund/dispute revisions fence further dispatch; late legitimate cost settlement remains possible without restoring execution authority.

The included owner path requires an explicit existing allowance reference and sufficient total authorization. It does not synthesize credits, a payment, or subscription membership. Reconciliation/risk completion does not verify physical scale. Length, area and volume remain pending until the existing reference/calibration and human review rules are satisfied; missing quantities are not zero, and a construction estimate is not fabricated.

SQL500 owns purchase, stages and authorization. SQL700 owns photo bridge execution metadata, source/profile identity, nonce/fence replay controls and one dispatch CAS; both use the existing spend ledger. Bridge transport carries no provider credential to the local worker. A completed remote result may be attached under a renewed lease without another dispatch; an unresolved dispatch cannot be replayed.
